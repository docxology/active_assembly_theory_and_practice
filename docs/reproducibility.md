# Reproducibility Manifest

`src/reproducibility.py` records the generated artifact surface that supports
the current manuscript and validation report. It writes:

- `output/data/reproducibility_manifest.json`
- `output/data/reproducibility_manifest.md`
- `output/figures/artifact_hash_manifest.png`
- `output/figures/README.md` (a caption ledger documenting every figure)
- `output/data/figure_registry.json` (the live canonical figure contract)
- `output/figure_atlas/index.html` (the offline accessible visual atlas)

The rendered PDF has a separate post-render audit at
`output/data/pdf_accessibility_report.json`. It is intentionally not folded
into the byte manifest because the report describes the PDF and would create a
self-referential freshness cycle. The report must be regenerated after every
render and must pass alongside the strict build-provenance check.

The combined DOCX has a separate post-render receipt at
`output/data/docx_render_receipt.json`. The complete composition, native cover
projection, source/media binding and PDF/UA workflow are maintained in
[document rendering](document_rendering.md). Use
[verification](verification.md) for the strict existing-output boundary;
regeneration after export changes the consumed scientific inputs.

Each manifest row records:

- project-relative artifact path;
- artifact class;
- generator module or function;
- file size in bytes;
- SHA-256 digest;
- linked claim IDs;
- linked validation checks;
- required/present status.

The manifest intentionally excludes self-referential and validator-produced
artifacts: the manifest JSON/Markdown, the manifest figure, the validation
report, the validation summary figure, and manuscript variables. Those files
are generated around the manifest rather than treated as stable inputs to it.

Validation recomputes the current size and SHA-256 digest for every tracked
artifact. A stale, edited, replaced, empty, or missing artifact fails the
`reproducibility_artifact_manifest` check even when the path still exists.

This is a reproducibility and freshness contract, not a scientific-validity
certificate. It can say that a rendered manuscript is pointing to the same
bytes the validator inspected; it cannot say that the model is the best model
for program semantics.

## Visual-bundle lineage

The figure bundle is generated after source receipts and before manuscript
hydration. `src.figure_contract.build_figure_specs` resolves all input paths and
hashes, while `src.visual_atlas` generates the nine narrative figures from the
formal, quotient, sensing, replay, and theorem receipts. The remaining
diagnostic figures retain their established producers but receive the same
canonical registry projection. PNG hashes are checked directly; native SVG/PDF
exports are parsed, and the atlas registry must have exact figure/figcaption,
alternative-text, and long-description parity.

The atlas is an offline accessibility surface, not an additional analysis
runtime. It deliberately exposes source digests and status semantics without
embedding protected labels in public model inputs. A source or protocol change
requires the bundle and manuscript variables to be regenerated before any
rendered document is considered fresh.

## Current research-extension receipts

The manifest includes the source-bound research surfaces for the current

  `uv run python scripts/run_formal_verification.py`. The command invokes the
  pinned Lean toolchain in `formal/`, hashes the checked `.lean` sources, and
  writes a deterministic theorem/build receipt. A local build is not an
  independent proof audit.
- `output/data/cross_architecture_fixtures.json` is generated through the real
  Capstone and Unicorn adapters by the advanced-inference producer. Its
  freshness check recomputes all three transparent architecture rows rather
  than trusting the JSON summary.
- `output/data/active_information_frontier.json` is generated from the
  label-blind factorized model and exact finite-horizon dynamic program. Its
  freshness check reruns the finite branch enumeration, including the declared

  `output/data/sensor_cost_receipt.json` records the eight-component

  calibration; neither artifact is a universal cost law.

- `output/data/replication_manifest.json` binds the public label-separated

- `output/data/counterexample_search.json` binds the smallest-first exhaustive

The active protocol is `output/data/research_protocol.json` at schema 2.2.0
(`active-assembly-open-roadmap-v2-2026-10-13`), which freezes the
temporal-corpus split. All receipts rebind on regeneration: a protocol
revision deliberately invalidates previously generated receipts rather than
being silently absorbed by them.

These receipts are bounded implementation and computational-evidence surfaces,
not independent replication, external-validity, or broad-theorem certificates.

The external-source receipt is intentionally separate from the transparent
fixture receipts. It accepts only a pinned manifest with immutable revisions,
license evidence, archive hashes, and an allowlisted static compile command.
The current manifest has ten rows across five projects and two revisions per
project. Static compilation/Capstone coverage and source-level label contracts
remain separate gates: the generated contract currently contains 100 accepted
rows (40 lexical-equivalence witnesses, 40 contract-directed near misses, and
20 identity negative controls), with the `libyaml` project held out for test
scoring. These labels are source-contract evidence and static lineage checks;
they are not a universal semantic-equivalence proof and are not derived from
model predictions. Separately operated replay remains a separate gate. Replay
and manuscript generation are no-network operations, and no arbitrary emitted
object is executed. `probe-capabilities` counts a target only after a static
object is actually produced; compiler target advertisements alone do not pass
that gate.

The explicit acquisition attempt is recorded separately at
`output/data/external_acquisition.json`. Its receipt binds the current
manifest and acquisition producer, records whether network access was actually
used, and retains one row for every pinned source rather than treating a
partially acquired corpus as complete. A verified cached archive may be reused
without network access; a wrong cached digest is rejected without overwriting
the cache, and a network download is published only after digest verification.
Extraction is staged and license bytes are checked before the source directory
is replaced. The artifact validator repeats these checks offline against the
local cache, so a changed manifest, producer, archive, or license file makes
the receipt stale. This improves provenance freshness but does not satisfy the
separate acquisition/build replay requirement for P13 promotion.

The source-bound label producer is `src/external_labeling.py`, configured by
`configs/external_label_design.yaml`, and writes
`output/data/external_label_contract.json` plus the generated
`configs/external_label_contracts.yaml`. Every accepted row binds the pinned
source and revision, the exact source edit and its contract argument, base and
pair source/object/disassembly digests, the explicit static compiler command,
and `execution_performed=false`. Rows that cannot satisfy the source, build,
decode, or labelability contract remain explicit exclusions rather than being
dropped from the denominator. Regenerate it with:

```bash
uv run python scripts/run_scientific_program.py label-external
uv run python scripts/run_scientific_program.py validate-external
uv run python scripts/run_scientific_program.py audit-external-preparation
```

`audit-external-preparation` is offline by construction: it rehearses the
pinned manifest parsing, license-file checks, archive safety, static-only
compilation, build reproducibility, source contracts, and exclusion accounting
against the on-disk cache and writes
`output/data/external_corpus_preparation_audit.json`. It reduces P13
operational risk without using any row as an efficacy claim.

The generated `external_label_coverage.png` is a provenance census of those
accepted contracts: its role bars and project/revision split matrix are derived
from the receipt, use direct counts and hatching, and mark the held-out project
without converting excluded or unavailable rows into performance zeros. It is
an audit surface, not an external-accuracy result.

The public replay directory also contains a protocol manifest, toolchain
receipt, and offline instructions. Its bundle digest excludes private gold
labels. Once a public bundle has been generated, its toolchain receipt is
treated as a frozen input: manuscript regeneration does not rewrite the
platform-specific receipt merely because the owner workstation received an
OS or package update. The current producer environment is retained in the
owner-side receipt envelope. An intentional protocol or public-bundle refresh
must explicitly reseed the public directory and obtain a new replay receipt;
it is not an incidental side effect of rendering.

A receipt produced by `write-replay-receipt` remains
`submitted_pending_verification`; protected ingestion requires a separately
controlled-run attestation before it can emit `independent_replay_observed`.
The current checked-in endpoint is `not_yet_observed` (see
`output/data/replication_manifest.json`): the retained same-host guest receipt
at `output/replication/replay_receipt_same_host.json` is still
`submitted_pending_verification`, and no separately operated receipt has been
ingested into `output/data/independent_replay_receipt.json`. When that endpoint
is eventually observed, it will still be controlled replay of the frozen
interface, not independent reimplementation or an independent physical-machine
result.

The public operator surface is intentionally usable without the owner-side
gold directory: `verify-public`, `replay --offline`, and `run-model` read only
the four files under `output/replication/public/`. `verify-separation` performs
the stronger public/private check when protected gold is present and falls back
to the public-only contract when it is absent. This prevents an operator VM
from regenerating or receiving the protected labels merely to validate the
replay interface.

For a same-host controlled replay, `configs/replay_vm.yaml` and
`docs/replay_vm.md` define the pinned Lima/Ubuntu ARM64 environment and blue-
backed storage contract. `vm-provision --allow-network` is the only VM command
that may acquire the pinned image, Linux `uv` archive, or guest packages.
`vm-replay` runs the public-only commands inside a guest network namespace and
requires a loopback-only interface proof. `vm-attest-replay` adds the explicit
same-host control scope before protected scoring. This can establish a
separately controlled replay receipt, but it cannot be promoted as an
independent physical-machine run or independent reimplementation.

The native Julia lockfile is itself a reproducibility input, not an incidental
developer convenience. `src.rxinfer_bridge.validate_julia_manifest()` parses
the committed `julia/ActiveAssemblyRxInfer/Manifest.toml` before either native
producer runs and requires its Julia and RxInfer entries to match the pinned
bridge constants. The integration gate resolves the exact Julia executable,
checks its reported version, and then runs the real Julia package tests. This
prevents a compatible-but-different local environment from silently replacing
the environment that produced the manuscript's native free-energy values.

The October 13 producer record extends beyond the pinned scientific toolchain. The

behavioral-validity evidence.

The producer order is material: regenerate source-bound data first, then
figures and figure metadata, then manuscript variables and hydration, then
render the configured editions, and finally run accessibility, freshness, and
provenance gates. Hand-editing a generated receipt, figure caption, or hydrated
manuscript is not a reproducible repair and will be overwritten or rejected by
the next gate.
